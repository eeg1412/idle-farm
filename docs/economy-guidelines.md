# 经济与数值准则

- 适用：新增或修改品项、配方、设施、工位、研发、品质、永久科技、RP、离线、任务、存档迁移的任何人（含子代理）。
- 优先级：`AGENTS.md` ＞ 正式式样（`docs/expansion/*`、`docs/game-design.md`）＞ 本准则。本准则不改写现行规格：凡与现行条文冲突的条目都标为【v3 采纳后生效】，在用户采纳 LT-2026-11-v3 并同步修改 `AGENTS.md` 与式样之前，按现行条文执行，不得单方面按本准则改数据或代码。
- 依据：[ECO-01 方案](reviews/2026-11-16-economy-rebalance-plan.md)（下称“方案”，P1–P12 为其 §1 问题编号）。`docs/balance.md` 是历史归档，不作依据。
- 本文的现状数字均由只读脚本对 `src/content/game-data.json`（balanceVersion=LT-2026-11-v2）静态展开得出，未运行游戏、测试、模拟或构建。

## 0. 记号与检查口径

| 记号 | 定义（数据来源） |
| --- | --- |
| `t` | `items[id].durationMs / 1000`，秒 |
| `out`、`p` | `items[id].output`、`items[id].price`（十进制字符串，按 BigInt 读） |
| `r(id)` | 原料（kind C/L/F）单设施 1 级基础金/秒 = `p·out/t` |
| `U(id)` | 单线产值：原料 `U=r`；配方 `U=p/t`（一个 1 级工位每秒流过的产值） |
| `V(id)` | 配方投入现值 = Σ `items[id].inputs[i] × p(i)`（品质 1 口径） |
| `Total(id)` | 研发总价 = `research[id].coins` + Σ `research[id].costs[i] × p(i)` |
| `k` | 设施等级 − 1；`L` 为工位等级 |
| `T` | 跨轮累计真实完工产值 `lifetimeProductionValue` |
| 回本秒 | 一次花费 ÷ 该花费带来的每秒新增收入 |
| 引导覆盖节点 | 在 `docs/expansion/07` 覆盖表中逐项列出、价格不按公式生成的节点（v3 草案为 P01、IL01、IF01、IL02、PD01） |

标注：【不变量】任何版本都必须满足；【v3 参数】数值取自方案，v3 采纳后生效；【现状】现行 v2 的满足情况。

## 1. 金币尺度与数值类型

**E-01 BigInt 与十进制字符串【不变量】**
- 规则：金币、件数、库存、产值、T、prestigeCredit、RP、任务奖励全部用 BigInt；存档与 `game-data.json` 中的经济数量（`price`、`output`、`inputs`、`coins`、`costs`）为匹配 `^(0|[1-9]\d*)$` 的十进制字符串。浮点只允许出现在生成器计算阶段，写入数据前必须取整（ceilDiv 或 3 位有效数字）。运行代码中的除法一律为整数除法，取整方向在式样中写明。
- 原因：AGENTS.md 规定；方案 §9 指出后期金额达 10¹⁷–10²⁰，超出 `Number` 安全整数（约 9×10¹⁵）。
- 检查：遍历 `items`/`research` 的上述字段做正则匹配；在 `src/game` 中检索经济路径上的 `Number(`、`parseFloat`、`Math.` 调用。
- 违反：拒绝合入；改为 BigInt 实现。
- 现状：满足。

**E-02 最低基价保证每级品质都涨价【不变量】**
- 规则：所有品项 `p ≥ 9`。等价于品质售价公式 `P(p,q)=p+⌊12p(q−1)/100⌋+⌊p·max(q−10,0)²/1000⌋` 在 q1→q2 时增量 `⌊12p/100⌋ ≥ 1`。
- 原因：P6，小麦 q2 花约 128 金加材料后单价仍是 3→3。
- 检查：`min(items[*].price) ≥ 9`。
- 违反：整体提高金币尺度（按 E-03 联动），不得单独抬某一项价格。
- 现状：**违反**，C01=3、C02=5、C03=8。【v3 参数】全体金币 ×10，最低基价 30（C01），q2 增 3。

**E-03 起始金币与尺度联动【不变量】**
- 规则：(a) `startingCoins ≥` 首块可购买农田报价，且 `≥` 引导第一个研发节点（P01）的金币；(b) 若金币尺度乘以 s，同一版本内必须同时换算：全部售价、设施/工位购买与升级系数、研发金币、品质金币、任务奖励与金额类任务阈值（如 `farmIncome`）、`startingCoins`；存档中的 `coins`、本轮 `productionValue`、`lifetimeProductionValue`（T）一次性 ×s；RP 常数换算到“同一进度得到同样的 RP”。
- 原因：方案 §3.1、§6；只换算一部分会让旧档凭空变富或变穷，或让 RP 随尺度膨胀（P5）。
- 检查：在 `world.js` 读 `startingCoins` 与 `facilityOffer(world,'C')` 新档报价；对照方案 §6 迁移表逐项核对换算清单。
- 违反：补齐换算或撤回尺度变更。
- 现状：(a) 满足（60 ≥ 60、60 ≥ 35）。【v3 参数】600 ≥ 600、600 ≥ 120。

## 2. 原料定价

**E-04 原料收益随周期严格递增【不变量】**
- 规则：同类主线按 ID 顺序（C01–C50、L01–L10、F01–F10，周期递增）相邻 `r(下一项)/r(上一项) ≥ 1.05`。分支品种（C51–C68）的 `r` 与“同周期主线公式值”偏差 ≤ 1%；周期相同的两项 `r` 相等。
- 原因：P2，C17–C27 单田 7.57–8.86 金/秒几乎持平，中段没有梯度。
- 检查：按定义计算 `r` 并逐对比较。
- 违反：回到生成公式修正，不在数据里手调单项。
- 现状：**违反**。C01–C50 中 7 对不升反降或持平（C04≤C03、C19≤C18、C22≤C21、C25≤C24、C43≤C42、C44≤C43、C45≤C44），23 对增幅 < 3%。L、F 主线满足。【v3 参数】`r = κ·5t²/144`，`price = ceilDiv(5κt³, 144·out)`，κ：C=1、L=F=10；C01–C50 相邻最小增幅约 6%（C39→C40）。

**E-05 跨类收益倍率等于费用倍率【不变量】**
- 规则：牧场/鱼池的购买与升级费是农田的 `factor` 倍（`world.js` `facilityTypes`，现为 10），则同周期的 `r_L(t)`、`r_F(t)` 必须等于 `factor × r_C(t)`，偏差 ≤ 1%（`r_C(t)` 取作物主线公式在该周期的值）。
- 原因：P1，费用只贵 10 倍、收益却是小麦的 14–40 倍（鸡蛋 6.88 金/秒，小麦 0.5）。
- 检查：对每个 L/F 计算 `r/(factor·r_C(t))`。
- 违反：改原料定价公式或 factor，两者同版本一起改。
- 现状：**违反**，按“不长于其周期的最近作物”静态比较约为 0.62（F04）–1.20（F05–F10）。【v3 参数】κ=factor=10，偏差 0。

## 3. 加工增值

**E-06 加工品必须比直卖投入赚钱【不变量】**
- 规则：每个配方 `p(id) ≥ ⌈1.2·V(id)⌉`（品质 1 口径，增值率 ≥ 20%）。新增配方同样适用。输入品质高于产物品质时机会增值可以为负，这是允许的专业化取舍，任务与 UI 不承诺其为正。
- 原因：P4，P13 增值 +4%、PT08 0%、PL06 +1%、PD11 +1%，加工不如直卖原料。
- 检查：对 `items` 中 `inputs` 非空的 437 项计算 `p/V − 1`。
- 违反：改配方定价公式，不改输入种类或数量。
- 现状：**违反**，437 项中 269 项 < 20%，121 项 < 5%，最低 PT20 0.37%。按类低于 20% 的数量：I 4/127、IL 6/10、IF 6/10、P 146/180、PL 19/20、PF 20/20、PD 18/20、PT 50/50。
- 【v3 参数】`price = ceilDiv(m·V·144 + ω·t·5κ_ref·t_ref², 1000·144)`，m/ω（‰）：I/IL/IF 1200/500，P/PL/PF 1300/750，PD 1350/875，PT 1400/1000；各类最低增值率 I 28.7%、IL 38.8%、IF 37.9%、P 33.2%、PL 45.8%、PF 44.7%、PD 44.4%、PT 48.1%（方案 §3.3）。

## 4. 设施：产量、升级与购买

**E-07 产量倍率按比例作用于基础产量【不变量；公式变更 v3 采纳后生效】**
- 规则：设施产量写成 `⌊base × 等级倍率(k) × 科技倍率⌋`，任何等级或科技项都不得以与 base 无关的绝对件数相加。由此同等级、同科技下两品种的产量比等于 base 比，收益排序与 `r` 排序一致。
- 原因：方案 §3.4、P8。现行 `base + k + ⌊k²/64⌋ + 2·增产级` 让 base=1 的 L01/F01 每级翻倍、base=6 的 C50 每级只 +17%；增产满级 +100 件，对 base 2 的 1 级田等于 ×51。
- 检查：任取两品种、多个等级，比较 `facilityOutput` 之比与 `out` 之比（允许取整误差 1 件）。
- 违反：退回式样。
- 现状：**违反**，且现行 AGENTS.md 规定“三类增产每级每批额外+2件”，在用户采纳前不得改。【v3 参数】`M(k)=1+k+⌊k²/64⌋`，`output=⌊base·M(k)·(100+2Y)/100⌋`。

**E-08 升级费曲线没有墙【不变量】**
- 规则：设 `Δ(k)=total(k+1)−total(k)` 为本级费用，则对所有 k ≥ 5：`Δ(k+1)/Δ(k) ≤ 1.5`；设施等级无上限；报价按“端点累计差 + 折扣后取整”。
- 原因：P7，现行 S(k) 在 k>14 后进入 x⁷ 项：16 级 37,204，20 级 446,478，25 级 4,463 万，30 级 6.84 亿。
- 检查：用 `facilityUpgradeTotal` 的公式对 k=5…400 逐级算 `Δ` 比值。
- 违反：换平滑曲线族，不加等级上限掩盖。
- 现状：**违反**，最大相邻比 4.18（k=17）。【v3 参数】`S'(k)=k(k+1)(2k+1)/6 + ⌊k⁶/24000⌋`，`A_C=300`、`A_L=A_F=3000`，最大相邻比 1.48（k=5）。

**E-09 升级优先于新购【不变量】**
- 规则：在方案 §3.4 ROI 表的每个参考阶段（首小时、首日、第 2 周、第 3 月，或任何经批准的阶段模型状态），“全体设施再升一级”的回本秒 ≤ “新买一座并升到同级”的回本秒；按此最优策略的常驻设施数每类 ≤ 20，上限 40 只在极后期有意义。
- 原因：P7，第 40 座农田仅约 5 万，后期就是不断开新线。
- 检查：以 `facilityOffer` 的购买与升级公式，按方案 §3.4 的“z、n、等级”参数重算两列回本秒。
- 违反：提高购买几何倍率或降低升级系数，二者择一并重算本表。
- 现状：**违反**，购买 `60×1.2ⁿ`，首小时“再升一级”509 秒、“新购”136 秒（新购更优）。【v3 参数】购买 `600×5ⁿ`（牧/渔 `6000×5ⁿ`），四个阶段升级回本均短于新购 1.8–6 倍；估算常驻农田 13–19 块。

## 5. 工坊工位

**E-10 工位升级语义【用户已批准新增玩法；增长公式待用户确认；v3 采纳后生效】**
- 规则（暂按“每级每批 +1 件”）：工位字段 `level`（十进制字符串，新建与旧档默认 `'1'`）；每批产出 L 件、每种投入 ×L、输入种类与周期不变；升级从下一批起生效，当前批 `batch.amount`/`batch.inputs` 为开批快照；换配方或清空按 `batch.inputs` 原样退回；缺料时等待整批，不做部分批次；不新增降级按钮；工位升级不享受任何折扣科技；`sellFarm` 重建为 `level '1'`。
- 原因：P4、P9，设施产量放大后，工坊每批 1 件只能靠铺满 48+32 个工位消化。
- 检查：式样 `docs/expansion/01` §1.1 已写入上述语义后才可实现；数据层核对 `stationRequirements`、`makeBatch`、`sellFarm` 与式样一致。
- 违反：未经用户确认增长公式前，不得写入式样或代码。若用户改选“与设施同为 M(k)”，按方案 §3.5 备选参数（`A_I/A_P=3000/3800`）。
- 现状：工位不能升级。【v3 参数】购买 `750/950×25ⁿ`，上限 48/32；升级 `A·[j(j+1)(2j+1)/6+⌊j⁶/24000⌋]`，`A_I=750`、`A_P=950`。

**E-11 工位数量不得成为管理负担【不变量】**
- 规则：任一阶段，按“回本更短者优先”的策略，每类（加工/精制）常驻工位数 ≤ 12；超过该数后“再升一级”的回本必须短于“新购并升到同级”。
- 原因：P9，48 个加工位总价约 200 万，产量放大时只能堆工位数。
- 检查：按方案 §3.5 ROI 表方法计算各代表配方的平衡数量。
- 违反：调整工位购买倍率（不改上限）。
- 现状：**违反**（无升级，规模只能靠数量）。【v3 参数】平衡数量入门 2、首日 4–5、后期 8–9。

## 6. 新产线解锁与研发

**E-12 研发总价随单线产值单调【不变量；v3 采纳后生效】**
- 规则：除引导覆盖节点外，把 523 个研发节点按 `U` 升序排列，`Total` 不得低于任何 `U` 更小节点的 `Total` 的 99%（`U` 相差 ≤ 1% 的并列分支允许相等）。
- 原因：P2、P3，C13 研发 2,460 金低于 C12 的 3,750；L01 总价 278 远低于 C12 的 13,856，而 `r` 是其 2.3 倍。
- 检查：用 §0 定义计算 `U` 与 `Total` 后排序扫描。
- 违反：改研发生成规则，不逐项手调。
- 现状：**违反**，全部节点中 495/523 项低于前序最大值；原料节点 63/87 项倒挂。注意：现行 `docs/expansion/06`、`07 §7.4` 规定研发 coins/costs/requires 逐项保留原值，在用户采纳 v3 前不得改研发数据。【v3 参数】`Total = 2·B(U)`，B 在 log10(U) 上按锚点 5:100、9:650、200:5.5×10⁵、3,125:2×10¹³、31,250:7×10¹⁵、420,000:7.5×10¹⁶ 分段插值。

**E-13 新产线的解锁门槛不得低于更低档品种【不变量；v3 采纳后生效】**
- 规则：定义 `G(id) = (Total(id) + 该类首座购买价) / r(id)`（已有同类设施时首座价记 0）。新设施类别的第一个节点（L01、F01 及今后新增类别）满足 `G ≥ max{G(x) : x 为 r(x) < r(id) 的原料节点}`。新增任何原料节点同样要满足 E-12。
- 原因：P1，L01/F01 只需 260 金 + 6 小麦、前置仅 C01，开局几分钟就能跳过整条作物线。
- 检查：按定义计算；首座价取 `facilityOffer` 对空类别的报价。
- 违反：抬高该节点研发总价（按生成规则），不加日期锁、不加额外前置。
- 现状：**违反**，G(L01) ≈ (278+600)/6.88 ≈ 128 秒，低于 G(C13) ≈ 2,556/4.77 ≈ 536 秒。【v3 参数】G(L01) ≈ 5,530 秒 > G(C13) ≈ 3,970 秒。

**E-14 研发金币与材料比例【不变量；v3 采纳后生效】**
- 规则：除引导覆盖节点外，每个节点材料现值占 `Total` ≤ 40%（即材料现值 ≤ 金币 × 2/3）；每种材料件数 ≤ 产能上限：原料 = 10 座设施 × H 小时 × 参考等级产量，加工品 = 4 个工位 × H 小时 × 参考工位等级；材料至少 1 件；金币至少 10。材料种类与 `requires` 不变（AGENTS.md）。
- 原因：P3，523 项金币合计 348,567,051，材料现值 4,594,727,006（13 倍）；C47 材料现值 5,186,048 对应金币 15,060。玩家无法从报价判断代价。
- 检查：对每个节点计算材料现值/Total，并按方案 §3.6 的 `k_ref`、`L_ref` 计算件数上限。
- 违反：退回生成器。
- 现状：**违反**，434/523 个节点材料现值 > 金币，最大比值 I100 约 5,453 倍。【v3 参数】H=4 小时；目标材料份额 = Total/3；`k_ref = max(0, round(130·log10(U/153)))`，`L_ref = 1+⌊k_ref/2⌋`；材料按产能封顶后后期份额降到 0–20%。

**E-15 研发只依赖逐项列出的条件【不变量】**
- 规则：研发只看 `research[id].requires` 与一次付清的 coins/costs；不加日期锁、不加分期进度；不改既有物品 ID、前置和耗材种类。
- 原因：AGENTS.md；方案授权边界。
- 检查：生成器 `preserveStructure` 比对旧快照的 requires 与 costs 键集合。
- 违反：拒绝合入。

## 7. 品质

**E-16 品质金币与单线产值成正比【不变量；v3 采纳后生效】**
- 规则：同一目标品质级，`品质金币(id, q→q+1) / U(id)` 对所有品项相同（取整误差 ≤ 1 金），不得按品类另乘系数；售价公式 `P(p,q)` 不变；品质材料规则与折扣规则不变。
- 原因：P6，L/F 的品质金币另 ×10 且引用 cropReferences，系数与真实产出无关。
- 检查：用 `qualityOffer` 的金币因子除以 `U`，求全体品项最大/最小比。
- 违反：改为统一公式。
- 现状：**违反**，现行因子 `(20+4p)`（L/F 为 10×参照作物）除以 `U` 后，最小 F01 约 53、最大 PT50 约 7,200，相差约 135 倍。【v3 参数】`Qc(q)=200·[(q−1)q(2q−1)/6+⌊(q−1)⁶/24000⌋]`，`coins = ceilDiv(Qc(目标)·U_num, U_den) − ceilDiv(Qc(当前)·U_num, U_den)`，`U_num/U_den = price·output·1000/durationMs`。

（每级必涨价由 E-02 保证。）

## 8. 永久科技

**E-17 费用、上限与前置【不变量，内容以 AGENTS.md 为准】**
- 规则：24 项共用 `techLevelLimit=50`；第 n 级费用 `(B/25)×[25+5(n−1)+(n−1)²]`，B=25/50/75/150 分组，24 项总 2,151,000 RP；高阶要求对应基础满 50 级和原品项前置；只能用 RP 购买。
- 原因：AGENTS.md 现行条文；方案 §3.8 也保持不变。
- 检查：`advancement.js` 的 `techBaseCosts` 与费用函数逐级求和 = 2,151,000。
- 违反：任何改动须用户明确批准并先改 AGENTS.md 与 `docs/expansion/01 §1.3`。

**E-18 单项科技效果上限【不变量；增产项 v3 采纳后生效】**
- 规则：单项科技满级效果 ≤ ×2（产量、速率）或 −50%（价格）；同一品项叠加后周期速率 ≤ ×2.5；产量类效果必须是百分比乘算（见 E-07）。
- 原因：P8，增产满级 +100 件压倒基础产量和设施等级。
- 检查：读 `advancement.js` 每级常数 ×50；对配方按 `rate()` 叠加最多的情形（PD：工坊 +100%、两项精制各 +25%，合计 ×2.5）核对。
- 违反：降低每级系数。
- 现状：提速、降费、评估满足；三类增产**违反**（且为现行 AGENTS.md 规定）。【v3 参数】增产 +2%/级，满级 ×2。

## 9. RP 来源与领取

**E-19 RP 只有两个入口【不变量；第二个入口 v3 采纳后生效】**
- 规则：(a) 活动权益：真实完工时按产值累计 T 与评估倍率（整数基点、BigInt）记入 `prestigeCredit`，只在原 `sellFarm` 成功提交中领取，0 产值也可出售，余数留存；(b) 任务 RP：只在 `settleTaskRewards` 的成功提交中计入 `researchPoints`，不进入 T/credit，不乘评估倍率。读档、解码、导入、离线结算、开发测试模式均不得发 RP；不得新增领取按钮。
- 原因：AGENTS.md“评估权益……只在原sellFarm领取”；方案 §4.1、§7。
- 检查：在 `src` 中检索 `researchPoints +=`、`researchPoints =`，确认只出现在 `settlePrestigeLedger`、（v3）`settleTaskRewards` 与迁移换算中。
- 违反：拒绝合入。
- 现状：(a) 满足；(b) 现行规格禁止任务发 RP，需用户采纳 v3 并按方案 §7 改 AGENTS.md 与式样后方可实现。

**E-20 RP 曲线标定【不变量；常数为 v3 参数】**
- 规则：`RP(T)` 为 T 的凹函数，指数 ≤ 1/2；入门阶段（0–2 小时参考产值）可得 RP < 25（不足一个 B25 科技 1 级）；按经批准的阶段模型，24 项科技全满所需时间在 12–18 个月；金币尺度变化时按 E-03 联动换算常数并递增 `prestigeLedgerVersion`。
- 原因：P5，`RP ≈ √(30T)`，首轮 3,000 产值即 300 RP，满科技只需 T≈1.54×10¹¹。
- 检查：用 `prestige-ledger.js` 常数计算 `RP(T) = isqrt(activityScale·T)·10000 / creditPerPoint`，代入方案 §5 的 T 时点。
- 违反：调 `activityScale`/`creditPerPoint`，不改科技费用。
- 现状：**违反**（`activityScale=30000000`、`creditPerPoint=10000000`，T=3,000 → 300 RP；T=10⁶ → 约 5,477 RP）。【v3 参数】`activityScale=49`、`creditPerPoint=5×10⁸`，`RP ≈ 0.00014·√T`；首售约第 1.5 天约 400 RP，全满约 432 天。

**E-21 任务 RP 总量上限【v3 采纳后生效】**
- 规则：全部任务 RP 合计 ≤ 科技全满总价的 2%（≤ 43,020 RP）；任务不发材料。
- 原因：任务 RP 不经 T，过多会绕开 RP 曲线；材料奖励会绕开 E-14 的产能约束。
- 检查：对 `taskResearchPointRewards` 求和。
- 违反：削减任务 RP。
- 【v3 参数】8 项合计 40,700 RP（1.9%）。

## 10. 离线

**E-22 离线上限【语义为不变量；时长为 v3 参数】**
- 规则：离线结算上限为整数毫秒、截断到上限、按锚点推进；离线结算不是成功经营事件，不计任务统计；离线期间只记真实完工产生的 T。0 级上限 ≥ 12 小时（每日 2 次回访不丢产出）。
- 原因：P12，8 小时起步时，每日回访 1–2 次的玩家前 40 级每天损失 0–16 小时产出。
- 检查：`advancement.js` `delegationMinutes(0)` ≥ 720；`world.js` 离线推进用 `Math.min(delegationMilliseconds, now−anchor)` 的整数结果。
- 违反：调整代管公式。
- 现状：语义满足；时长**违反**，且现行 AGENTS.md 规定 0/40/50 级 8/24/36 小时，用户采纳前不得改。【v3 参数】0/20/50 级 12/24/48 小时：`720 + 36·min(L,20) + 48·max(L−20,0)` 分钟。

## 11. 任务

**E-23 奖励按完成时刻的参考收入定价【不变量；I_ref 为 v3 参数】**
- 规则：每项金币奖励 = `round2(I_ref(预计完成时刻) × 60 × m)`，`0.5 ≤ m ≤ 60`（分钟）；入门主线 m ≤ 1，长期 m ≥ 20。修改金币尺度时同步改 `I_ref` 与金额阈值类任务。
- 原因：P10，前六项任务共 145 金，第 3 块地即 60；itemCollection 250,000 相对 PT50 研发 15,589,584 金可以忽略。
- 检查：用方案 §4.1 的 `I_ref` 表与附录 F5 的预计完成时刻重算每项 `reward/(I_ref·60)`。
- 违反：按公式重算，不逐项拍数。
- 【v3 参数】`I_ref` 锚点见方案 §4.1；67 项合计约 2.48×10¹⁶ 金。

**E-24 任务记账规则【不变量】**
- 规则：任务统计只随成功经营事件在同一事务中增加，失败回滚；奖励在下一次成功提交时由 `settleTaskRewards` 一次性发放，读档、解码、导入不发；奖励不计入售货数量、收入、产值、T/credit；`taskRewards` 已领列表不删、不追缴、不补差额；任务 ID 不重用。
- 原因：AGENTS.md；`objectives.js` 现有注释约束。
- 检查：新增统计字段只在对应动作成功路径中修改；`settleTaskRewards` 只改 `coins`、`taskRewards`（v3 另加 `researchPoints`）。
- 违反：拒绝合入。

**E-25 玩法覆盖【不变量】**
- 规则：`src/main.js` `actions` 白名单中每个产生成功经营事件的动作（及其主要分支，如改种），以及科技、代管、图鉴、出售牧场多轮，至少有一项任务引导。豁免：画布外的配方 Wiki、离线结算、`updateSettings`。新增动作必须同时新增任务。
- 原因：P11，现有 24 项未覆盖升级设施、改种、品质、工位购买/优先、保留量、批量出货、科技、代管、图鉴等。
- 检查：按方案 §4.2 的“玩法 × 任务”表逐行核对 `objectives.js` 的条件函数。
- 违反：补任务后才可上线该动作。
- 现状：**违反**，缺口 11 类（方案 §4.2）。

## 12. 旧档兼容与迁移

**E-26 ID 与结构不变【不变量】**
- 规则：不改、不重用既有物品/配方/任务/科技 ID；不改配方输入种类、研发前置、周期、基础产量，除非用户逐项明确授权；新内容只追加新 ID。
- 检查：生成前后比对 `items` 键集合与 `inputs` 键、`durationMs`、`output`、`research[*].requires`。
- 违反：拒绝合入。

**E-27 迁移一次、原子、不发奖【不变量】**
- 规则：每次换算以版本字段（`balanceVersion`、`prestigeLedgerVersion`、`schemaVersion`）为门，只执行一次；读档只生成迁移草稿，版本、换算和字段补齐在同一次原子保存中完成，失败全部回滚；已付的研发/品质/科技不重算、不补扣、不退还；未花 RP 只按换算规则处理一次（AGENTS.md：旧档等级数字不乘 10、旧未花 RP 仅 ×25 一次）；新字段缺失按明确默认值（如工位 `level '1'`、`stats.batchSales 0n`）。
- 原因：方案 §6；重复换算会让旧档资产成倍膨胀。
- 检查：对每个迁移函数确认“已是新版本即原样返回”，且不写 `taskRewards` 以外的奖励字段。
- 违反：拒绝合入。
- 【v3 参数】v2→v3：`coins`、本轮 `productionValue`、T 各 ×10 一次；未花 RP 不变；`prestigeCredit` 余数保留；工位补 `level '1'`。

## 13. 改动流程

**E-28 先式样后数据【不变量】**
- 规则：顺序固定为：①改 `docs/expansion/01`/`07`（及相关式样）写明公式与参数 → ②改生成器 `scripts/long-term-balance.mjs` → ③重新生成 `src/content/game-data.json` → ④改 `src/game`。不得手改 `game-data.json`；引导覆盖等例外必须写在式样表中由生成器读取。
- 原因：AGENTS.md“目录改动先编辑扩展式样，再生成新版运行数据”。
- 检查：同一提交中数据变更必须有对应式样变更。
- 违反：撤回数据改动。

**E-29 平衡版本号与变更记录【不变量】**
- 规则：任何影响价格、产量、费用、研发、品质、RP、离线或任务金额的改动，都递增 `balanceVersion`（格式 `LT-YYYY-MM-vN`），改 RP 常数或 T 口径时同时递增 `prestigeLedgerVersion`，存档字段变化时递增 `schemaVersion`；在 `docs/expansion/07` 记录新旧参数对照与迁移规则；与 AGENTS.md 条文冲突的改动先取得用户批准并更新 AGENTS.md。
- 检查：`game-data.json` 的 `balanceVersion` 与 `scripts/long-term-balance.mjs`、`prestige-ledger.js` 的版本常量一致，且 07 中有对应记录。
- 违反：补版本号与记录后才可合入。

**E-30 验证授权【不变量】**
- 规则：本准则中的检查均为静态计算；运行游戏、测试、模拟脚本、预览、构建、语法或运行时检查需用户明确授权，最终编译只由项目经理执行。静态计算或阶段模型不能替代实测完成天数（`docs/expansion/07 §7.6`）。

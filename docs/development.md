## 无人值守实装

- 主代理担任项目经理，使用 [farm-task-dispatch](../.agents/skills/farm-task-dispatch/SKILL.md) 组织项目任务指派、拆分与交接，具体实现交给文件所有者子代理。项目经理维护需求及持久反馈清单，负责拆分、输入摘要、所有权、接口冻结、依赖调度、汇总、整合实际执行路径、最终编译及用户同步。按独立成果物拆小任务；只有一个不可再分的输出时，仍使用一张任务卡和单一所有者，不为凑代理数量强拆。
- 每次指派采用 [任务卡](../.agents/skills/farm-task-dispatch/references/task-card.md)：提供背景与目标、上下文相关性及复用理由或新建上下文选择、agent↔objective↔artifact 对应、最小交接、精确输入及证据、最少读取文件和章节、与本任务有关的 AI 开发规约摘录及出处、可编辑文件和禁改范围、方法与接口依赖、成果物路径和格式、完成条件、允许验证及未验证项、汇报格式。项目经理先整理必要摘要，避免每个子代理重新探索全项目。
- 子代理上下文规约跨会话沿用：只有同一目标、连续成果物或直接依赖链的工作可以复用同一子代理；相同文件、同种工具、空闲或熟悉项目不单独证明任务相关。毫不相干的任务必须新建干净上下文（`fork_turns: "none"`），只传本任务必需资料和最小交接，不继承旧对话。槽位不足时排队或结束已完成任务以释放槽位，不把无关任务串入旧代理；连续微步骤不机械另建代理。最小交接包括接手目标、必需事实及证据位置、成果物与版本、冻结接口、剩余问题、授权范围和所有权状态。
- 文件所有权互斥，共享文件修改和共享资产生成各由一个所有者完成。记录代理、目标、成果物及所有权状态；转交时先明确结束旧所有权，再由新所有者接手，并交接实际成果物与未完成项。先冻结跨任务接口，再分配可并行任务；后继任务等待前置成果物和接口交接，不并发改写依赖输出。需要改接口、扩大读取或写入范围时，子代理先报告项目经理，由项目经理更新任务卡和相关任务。
- 子代理只读任务必需资料并完成指定小任务，不自行扩展范围，不覆盖或撤销其他人的改动。按接手、阶段完成、阻塞、交付持续汇报，说明输入、实际文件、接口、剩余项和验证状态；项目经理汇总后向用户定期同步。无人值守期间在已有授权内继续完成可独立推进的工作。
- 项目经理以实际调用路径和源证据核对交付，记录需求对应的接入点、完成情况及剩余限制；不能仅凭子代理报告、素材存在或测试数量宣布行为正确。用户再次报告失败时，重新打开持久反馈项，旧完成记录或通过的检查不能代替本次问题确认。
- 用户明确授权前禁止运行测试、冒烟、预览、试编译、语法或运行时检查，以及任何同类验证；创建 skill 也不授权运行其验证脚本。正常的文件阅读、实现、资源生成与转换属于交付工作。仅所有模块、资料与资源接齐后，由项目经理执行最终编译。
- 如需授权后的验收，使用 [验收步骤](verification.md) 与扩展式样书中的验收用例。

## 技术文档用语

- 技术文档必须明确陈述事实、要求、适用条件和当前状态。禁止使用“建议、尽量、酌情、适当、大概、差不多”等含糊措辞替代明确要求，不以提案或许可式表述模糊既定规格。
- 可选行为必须写明选择条件、允许范围和必须保留的边界；能力描述与条件分支必须指出具体对象和成立条件，不能仅写“可以处理”或“视情况而定”。
- 未知项标注“待确认”，逐项列出缺失信息；未执行验证或证据不足的结论标注“未验证”，说明缺少的验证或证据。禁止为了语气确定而将未知写成事实、将未验证写成通过，或伪造用户确认。

## 文档范围与长期设定

- 局部案例与当前名单的结论只适用于对应对象，不得推导为全局禁令或未来扩展限制；约束写明对象和成立条件。
- 长期设计正文正向陈述设定，保留真实用户要求与确定事实；任务状态、过程辩解和反复预防假想问题的文字留在任务记录，不混入正文。
- 只将真实需求写成约束，不得为了防止误解增添用户未要求的限制。

## UI 文案与缺陷处理

- 只显示当前操作必需的简短状态与反馈；禁止在UI堆积机制说明、异常成因和兜底教程，不让玩家承担阅读负担。
- 行为与用户设定不符时先查根因；不能用解释性“小作文”替代修复，不能把历史AI文档当成缺陷合理化的依据。

- 弹窗打开不暂停或清空已有管理员对白。打开资料不应额外触发气泡，与是否继续已有对白是两件事，禁止混为暂停规则。

## GitHub 推送授权

- 只有用户针对当前推送明确下达指示时，才能执行 `git push` 或通过其他工具、脚本向 GitHub 和其他远端推送。接管项目、实现功能、修复问题、最终编译和本地提交均不包含推送授权。
- 过去任务中的推送许可不延续到后续任务。每次需要推送时，必须先有对应的用户明确指示；禁止在完成本地工作后自行推送。
- 此约束适用于 `git -c ... push` 等命令变体和自动化流程。`.codex/rules/project.rules` 的命令提示只提供额外拦截，不替代用户授权，也不能通过改写命令绕过规约。

## 开发测试模式

这是用户明确要求的开发专用额外行为，不改变正式版玩法与正常研发规则。

- 仅 `npm run dev` 对应的 Vite `serve`、`mode: development` 启用。在 `/#/settings` 设置页连续点击页头标题「设置」11 下，第 11 下通过现有动作与存档事务发放。离开设置页或点击其他控件时清除未完成的点击计数。
- 发放内容为全部品种与配方解锁、42 项经营改良达到各自上限，以及追加1T金币，即 `1_000_000_000_000n`，并把时空胶囊持有数设为 144,000（[式样](expansion/10-time-capsule.md#109-开发测试模式)）。使用 `techDefinitions[].maxLevel`，金币按BigInt运算并按现有规则序列化；品质等级没有上限，不属于「全部科技满级」。
- 发放不得冒充正常经营事件，不增加生产、出售、售货收入或其他累计经营统计。成功反馈应在保存事务提交后出现；失败不得留下部分发放结果。
- 开发环境使用独立 IndexedDB 数据库 `idle-farm-v7-development`，正式环境使用 `idle-farm-v7`。开发测试获得的金币与科技不得写入正式存档。
- 开关必须由 Vite 命令类型与模式在编译时决定，不能仅依赖运行时页面、URL 参数、浏览器存储或 `NODE_ENV`。所有 `vite build`，包括 `vite build --mode development`，都必须移除标题触发器和发放模块；构建产物及 `npm run preview` 中不能启用该功能。
- 本功能的开发不构成运行测试或预览的授权。仍遵守本页的验证限制，全部模块完成后由主管执行最终编译。

## 素材

- 小图标按稳定 ID 排入大图的 5×5 透明网格，一格一件，留出足够透明带。确认分隔完整后裁切为单张。原图、规则裁切表和最终图标可按 ID 对照。
- 导航、设施、操作、任务和经营改良各用独立图标。物品图只在表示对应的作物、原料、中间产物或商品时使用。各页横幅独立绘制，界面参考图只用于确定构图、比例和色彩。
- 大图如各页场景逐张整幅绘制。保留全幅 PNG 原图，再按页面比例裁出使用区域并转成 WebP 质量 70。
- 每项新增作物交付一枚物品图标和一幅显示该作物长在地块中的定植场景。新增牲畜与鱼类同样各交付物品图标和设施场景；牲畜另交付独立透明选择图及完整动画资源。场景原图可按格随批维护，发布图为 `public/art/scene-<物品ID>.webp`，规格为 320×320、质量 70。逐格核对对象与 ID、边缘裁切和独立性。最终构建包含 `npm run art:check`，单独执行检查仍遵守用户验证授权。
- 实际界面的 WebP 按需请求，浏览过的游戏图片可由离线缓存复用。源图不进入构建或预缓存。运行时资源网址一律经 `assetUrl()` 生成，生产构建发布为带内容哈希的文件名，新增资源路径必须能由 `runtimeAssetPaths()` 推导，不手写版本号。详细规则见 [发布文件名与资源网址](assets.md#发布文件名与资源网址)。
- 审图证据图（合成、分镜、关键帧、接触表、对照图，例如 `assets/*/reviews/`、`assets/livestock/*evidence*/`、`assets/mining/keyframes/`、`assets/source/art/**/*review*/` 中的图片）每次审阅都可在本地生成，供 AI 和人审阅，不提交到仓库，`.gitignore` 已按目录忽略。`docs/art-reviews/` 报告与 json 证据清单及同目录合成脚本照常提交，记录证据图本地路径与 sha256，并注明“证据图仅本地保存”。新环境需要时用对应导出或合成脚本（如 `export-crop-animation.mjs`、`export-fish-animation.mjs`、`export-livestock-animation.mjs`、`compose-mining-keyframes.mjs`）重新生成。

### 作物成长动画

新增或改画作物使用 [farm-crops](../.agents/skills/farm-crops/SKILL.md) 及其按 ID 交付清单。当前覆盖目录全部 68 种作物，后续按目录扩展，不固定数量或遗漏图标、回退场景。

1. 以作物目录 ID 交付种子、幼苗、成长期、成熟期四种前景。植物原画用透明 5×5 网格绘制，独立单株保留足够格间空隙。逐格核对品种、花果、根脚和透明边，再裁切。成长期和成熟期必须有该品种的整株特征，成熟期的收获物画在植株上。
2. 全目录按 `assets/plot/crop-layout.json` 显式分大、中、小。C02–C68 使用每期独立单株图片，运行对每个根位创建一个 Sprite，不能把多棵树烘焙成一张整田前景替代逐株绘制。四期共用同一组固定根位。中、大型按 `crop-layout.json` 的 `fieldGeometry`（从田地底图实测的田垄线族、左右田地侧边与土面轮廓，附测量方法）建立田面透视：列族平行于田地左右侧边并汇向其消失点，排沿实测田垄脊线，排距随透视平滑递增、不得跳变；栅格铺满可见可种田面直到画面左右与近端边缘，边缘植株允许被130／320画框裁切，根脚须在实测土面轮廓内，不落草地或栅栏。近端不贴土／草分界：根脚离土面下沿至少留当地排距的 1/4（不少于 8px，`fieldGeometry.nearEdge`）；不满足的网格点沿所在列向远端后收，与同列前一株至少隔半排，不直接剔除；外侧列贴右下草线、后收仍不够的少数点，再沿所在田垄向田内平移不超过 0.35 列距（`fieldGeometry.sideEdge`），并与邻株保持距离，不整列加大内缩；仍放不下才剔除并报告。禁止用手标田垄端点充当列边界、为避免裁切空出边缘、固定两列窄带或跨排筛掉整排。根脚贴合背景，近大远小，远端按可用高度保留完整树冠，不被画面上缘截断。小型作物沿用 `furrows.json` 原根位。小麦原图、密度与尺寸保留。图层为天空、田地、后排逐株精灵、洒水器、水滴与飞溅、前排逐株精灵，前排可遮喷水。320图、根位叠图和130×138素材合成只用于审摆位，不能作为运行前景。
3. 唯一正式转换逻辑为 `node scripts/export-crop-animation.mjs`，Python旧入口仅以标准库转发Node，不再默认导出整田图，也不因缺Pillow阻断。C02–C68从已有 `assets/plot/crops/<ID>/{sown,seedling,growing,mature}.png` 分别导出一株；持久派生PNG在 `assets/plot/plants/<ID>/`，发布 `public/art/plot/plants/<ID>/<phase>.webp`，质量70、保留透明。`crop-visuals.json` 每ID登记 mode/size、roots（含x/y/row/column/scale/maxHeight）及每期 path/width/height/anchorX/anchorY/baseScale/source。loader加载四张独立单株，runtime逐根实例化，只在阶段切换时改各株texture/pivot/scale，根位固定；不在runtime测bbox。旧C02+整田图集已从发布目录移除，源图仍在 assets/，仅保留历史，不能作为活跃交付。C01仍从已认可wheat-0..3.png原稿使用fieldAtlas整幅例外，仅绘完整前景，不水平截麦穗、不虚构单株目录。
4. 作物另按 `crop-harvest.json` 显式分 `wholePlant`（整株采收）和 `retainedPlant`（保留植株采果、花或叶），与大小分类独立。展示没有保底，跟随真实批次时长 T 分三档（每阶段至少1秒，另留1秒）：整株采收 T≥5秒完整四期；3秒≤T<5秒只播种子与成熟两期；T<3秒只显示成熟期，不逐批淡出。前两档成熟末尾逐株层同步300ms淡出、留空30ms再种子。保留植株首次换种按首批时长套用同样四期三档，后续展示周期只在成年采后状态与成熟状态间变化：T≥3秒两态各占半程交替，不足3秒只显示成熟状态；成年植株底层不随采收消失。必须审现有真实单株能否作为成年采后状态；幼树不能放大冒充成年无果树。需补画时使用内置绘图工具从成熟单株精确编辑，保留独立源图、来源和实际根脚／尺度。每个真实批次从自身起点开始展示，不再放慢或跨批次延续相位；展示不新增经营事件。减弱动态设置已删除。
   C设施可选 `planting:{id,start,duration}` 保存首次换种的模拟起点与首批实际时长。同品种、升级和自动续批保留，换种重置；首轮直接按 `duration` 套用三档，结束后进入成年采收循环。已安排作物的地块直接保存播种起点和首批时长。存档版本、经济产量和任务计数不变。
5. PixiJS只为可见活跃种植卡创建动画，最近邻绘制。C02–C68按需加载该品种四张单株，四张齐全才创建逐株实例；C01仅加载原fieldAtlas。天空、田地和洒水器共用。滚出、换页、后台与弹窗底板完全遮住时卸载，普通弹窗打开时背后可见的动画继续播放；加载中／资源失败／资料缺失时保留动画区域，不显示回退图标、静态设施图或程序占位；所有WebP排除启动预缓存。
6. 正式构建的 `npm run art:check` 要覆盖目录中每一个作物 ID。发布前核对所有图集的尺寸、透明度、四帧完整性和 ID 对应，检查典型作物的种植位置及切换；在线检查按用户授权和 [验收步骤](verification.md) 执行。

### 畜牧动画

这是用户指定的展示行为，范围已从蛋鸡和黑猪样例扩展为目录全部 10 种牲畜。新增或改画使用 [farm-livestock](../.agents/skills/farm-livestock/SKILL.md) 及其交付清单，新增 ID 同步交付全部资源。经营数据、收成和任务统计保持原有规则。按 `src/view/livestock-layout.js` 显式分大小：鸡、麻鸭、肉兔为小型三只，鹅、番鸭为中型两只，牛、羊、猪为大型一只。动物、对应数量产物和各自程序阴影随站位深度缩放，按远到近绘制；展示数量不改变经济批量。

1. 固定背景是同一幅空牲畜棚舍。附属产品类保持成体，交付4张吃饲料idle原画；肉类幼年、成长、成熟各4张独立吃饲料idle原画。全种类和全部阶段都用低头啄食／咀嚼等真实绘制变化，不能靠旋转整只精灵或缩放静态动物代替。每帧300毫秒循环。每只动物有与真实口部落点对应的独立饲料层，按同一体型／站位透视缩放；饲料不烘焙进动物脚区。分类由 `assets/livestock/layout.json` 显式 `slaughter` 登记，并生成 `src/content/livestock-visuals.json`，不可按ID序号猜测。

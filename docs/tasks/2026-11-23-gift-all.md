# 角色管理全员送礼

PM：主代理。推送授权：无。测试、预览与运行检查：未授权（测试只写不运行）。最终编译由 PM 执行。

## 用户需求与决定

- 角色管理页底部增加吸附按钮「全员送礼」，一次给全部管理员（含行脚商 `merchant`）送礼。
- 默认算法先分每人的心愿物品，再分其他物品；玩家可在确认前调整最终方案。
- 默认只送到每人当天好感上限；提供「送出全部可赠额度」选项，并记住玩家偏好。
- 保护：已接受订单的商品及其全部上游材料（`orderItemTags(world)` 的 `products` 与 `materials`）不参与全员送礼；保留量与行脚商锁定量已由 `availableToProduce` 排除。
- 送出后各人卡片同时显示收礼反应（方案 a：心愿物品用 happy 表情与 `wantedThanks`，否则 smile 与 `thanks`），渲染不得浪费性能。

## 规则

- 送礼沿用单人送礼的全部经济规则：共享「还能赠送的礼物总值」`managerGiftRemaining`、好感资金 `affinityFundingRemaining`、每日好感上限 `managerDailyCap`、心愿 ×2、回礼累计。全员送礼只是一次提交多笔 `giftManager`。
- 角色处理顺序固定为 `managerIds`；同一份世界与偏好得到同一方案（无随机）。
- **只送到上限（默认，`giftAllMode: 'cap'`）**
  1. 跳过今日好感已满或好感资金为 0 的角色。
  2. 心愿阶段：逐个心愿物品（按物品 ID 排序），把库存分给想要它且仍有缺口的角色，缺口（`valueToDailyCap`）大的优先；每人取刚好让当日好感达到上限的最少件数（受库存、共享额度与好感资金约束；件数增加不再增加好感时停止）。
  3. 补齐阶段：缺口仍大于 0 的角色按缺口从大到小，用其余可送物品补到上限。可送物品为 `managerGiftLimit(world, id).available > 0` 且不受保护的物品，按可用件数从多到少、再按物品 ID 排序依次使用。
- **送出全部礼物额度（`giftAllMode: 'all'`）**：先执行上面两阶段，再把剩余额度按回礼比例从高到低（同比例按 `managerIds` 顺序）逐人送出其余可送物品，直到额度或可送库存用尽。
- **平均分配（`settings.giftAllEven`，默认关，记入存档）**：开关位于模式切换上方，两种模式都显示。送到上限时开启：可送额度（剩余额度与可送库存总值取小）不足以送满全部未满角色时，按各人送满所需价值做带上限的水位均分，每人先用自己的心愿再用其余物品，到上限即止；额度充足时结果与不平均相同。送出全部礼物额度时开启：上限阶段之后的剩余额度不按回礼比例集中，而按「至今所收礼物价值」水位填平：先算可送额度（剩余额度与可送库存总值取小）能把收礼最少的若干人抬到的同一水位，再按可送物品顺序逐人补到该水位；只用整件，可能留少量额度未送。
- 同一角色同一物品合并为一笔。方案为空时按钮不可用。
- 玩家调整后的方案在确认时整体重算报价；任一笔与确认时报价不一致或不可送，整笔不提交，界面刷新方案并提示「条件有变化，请重新确认」。
- 偏好 `settings.giftAllMode` 存档为 `'cap'` 或 `'all'`，缺字段按 `'cap'` 迁移，经 `updateSettings` 动作切换。

## 接口（两张卡共同遵守）

`src/game/managers.js` 导出：

| 函数 | 说明 |
| --- | --- |
| `giftAllProtectedItems(world)` | 返回受保护物品 ID 的 `Set`（锁定订单商品与全部上游材料）。 |
| `planGiftAll(world, mode)` | `mode` 为 `'cap'` 或 `'all'`，返回 `[{ id, itemId, count }]`（`count` 为 BigInt），按上节算法。 |
| `quoteGiftAll(world, gifts)` | 在世界副本上按顺序逐笔 `quoteManagerGift` 并应用，任一笔无效返回 `null`。否则返回 `{ gifts: [每笔报价], roles: { [id]: { before, after, gain, value, returnValue, wanted } }, value, remainingAfter }`；`before/after` 为当日好感，`wanted` 表示该角色收到至少一件心愿物品。不修改传入世界。 |
| `giftAllManagers(world, expected)` | 动作。`expected` 为 `quoteGiftAll(...).gifts`；逐笔重新报价，`giftQuoteTerms` 与 `count`、`itemId`、`id` 全部一致才依次 `giftManager`，否则返回 `false`。成功返回 `{ roles: [{ id, wanted, gain }], value }`。 |

`src/main.js`：`actions` 注册 `giftAllManagers`，反馈 `{ sound: 'success', giftAll: result }`；`updateSettings` 接受 `giftAllMode`（`'cap'|'all'`）。

## GIFT-UI 界面要求

- 角色管理页 `renderManagerDirectory` 用现有 `ui.footer` 吸附按钮「全员送礼」（gold 样式，可用 `actionIcon('gift')`）；还能赠送的礼物总值为 0 或没有可送的未保护物品时禁用；全员今日好感已满（或好感资金为 0）但仍有额度时保持可用，弹窗不显示偏好切换，直接按「送出全部礼物额度」生成方案，不改存档偏好。
- 点击打开「全员送礼」弹窗：
  - 顶部一行：礼物总值 / 还能赠送的礼物总值。
  - 偏好切换两项（filter 样式）：「送满今日好感」「送出全部礼物额度」，切换即 `updateSettings({ giftAllMode })` 并重算方案。
  - 12 人列表（`managerDirectoryOrder`）：小头像、名字、今日好感「送前→送后 / 上限」与进度条、计划物品图标×件数（心愿件标红「心愿」）；无计划的人显示「本次不送」。
  - 点一行打开该角色的调整弹窗（今日好感与进度条下方以分隔线与物品区隔开）：列出计划物品，每项用进度条调整件数（0 表示移除；100% 为该物品扣除其他角色同物品计划后的库存，各进度条互不联动；共享额度只在上拉时封顶件数），可添加该角色可送物品（受保护物品不列出；列表按库存列出，共享额度用完时行变灰不可点，不增减行数），可「本次不送」。调整只改弹窗本地方案，返回后汇总与列表按 `quoteGiftAll` 重算。玩家手动调整后切换偏好会重新生成方案。
  - 底部「取消」「确认送礼」；确认调用 `giftAllManagers` 动作。失败或打开期间库存减少导致报价失效时，保留玩家方案，只把超出当前库存／额度的项压到上限；仍无法报价才按当前世界重新生成方案并提示「条件有变化，请重新确认」（确认失败的提示由全局 toast 显示一次）。
- 成功后关闭弹窗，每个收到礼物的角色卡片显示收礼台词（`wantedThanks`/`thanks`，表情 happy/smile）。现有 `managerReplyRole` 只支持单人，需支持多人同时回复。
- 性能：不新增 ticker、不逐帧重建；逐字演出只推进视口内可见气泡（沿用现有不可见暂停）；头像复用现有纹理缓存与 `preloadGiftPortraits`；列表行数固定 12，不为每帧新建 Text。
- 文案只保留操作必需信息，不加机制解释。打开 Dialog 不暂停或清空已有对白（AGENTS）。
